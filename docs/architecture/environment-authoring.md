# Environment, lighting, and water authoring

Environment authoring is split into validated source definitions (`model/environment-authoring.ts`), stateless sampling (`runtime/environment-state.ts`), rendering environment evaluation (`runtime/environment.ts`), water realization and physical queries (`compiler/water.ts`, `compiler/river-channel.ts`), and the Studio domain panel. Existing documents remain valid because the new source fields are optional.

## Composition and time

An environment sequence contains 2–32 fully specified weather/light states with strictly increasing times inside a finite duration. States coordinate sun elevation and azimuth, haze, shallow fog, wind, ambient/direct intensity, surface wetness, exposure stops, and a linear RGB light tint. Linear or smooth interpolation is deterministic at arbitrary seek times. Loops interpolate the last state back to the first; azimuth takes the shortest circular arc. A non-looping sequence holds its endpoint states.

The runtime evaluates the same authored sequence for preview and game extraction. Wind feeds vegetation motion; wetness is merged into surface appearance by the scene host. Exposure multiplies the stage exposure by `2 ** stops`. Environment and stage grades compose with the sampled grade. Tint controls illumination (including physical sky/scattering through the solar spectrum), rather than being an arbitrary display-space saturation operator.

Lighting rigs can contain up to 16 composition zones. A zone uses either a sphere or an oriented room volume with authored half extents and yaw. Camera position determines a smooth blend in metres inside each zone boundary. Priority, followed by stable identity, determines overlap order. Zones blend ambient intensity, direct intensity, fog multiplier, exposure, and tint. They describe the viewed environmental state; local point lights continue to determine spatial illumination. They are not light probes, volumetric spotlights, baked indirect lighting, or a replacement for an interior lighting solution.

## Continuous atmosphere cost and evidence

The existing physical scattering table stores three extinction-independent density integrals per cell. `compileAuthoredAtmosphere` builds that table body once, then copies the body and replaces only the atmosphere coefficient header for subsequent weather samples. It does not integrate new rays on each frame or quantize weather values.

`extinctionUpperBound` makes the integrator certify the largest transmission interval width over every extinction coefficient in `[0, 530]`. The maximum of `exp(-k*lower)-exp(-k*upper)` occurs at an endpoint or `k = log(upper/lower)/(upper-lower)`. All authored haze/fog coefficients lie inside this interval. The basis uses a 0.0001 interval-width target and a cap of 256 integration segments. Tests record zero exhausted cells for the authored domain. Existing numerical and interpolation-error metadata remain explicitly unknown: this integration bound is not a blanket rendered-image error claim. Header rebinding costs about 0.02 ms per new weather state on the development host, following a roughly 60 ms first basis build; these are local measurements, not a cross-device performance guarantee.

## Water

Optional uniform X/Z current advects each wave by its projection onto that wave's direction. The compiler phase product, water shader submission, CPU height/normal query, and vertical surface velocity use the same resolved speed. The scene host clears the source flow field on render surfaces after baking speeds so CPU picking cannot apply current twice. Physics retains the authored definition and receives horizontal current for buoyancy drag.

Optional river points define a bounded flat-water ribbon with variable width and depth. A shared bounded-miter boundary drives both rendering geometry and wet/dry queries, including corners and capped ends. Dry samples cannot apply buoyancy. River current follows the centerline tangent and slows inside the authored shore width. A parabolic cross-channel depth profile exposes depth to interactions, and bank foam coverage is baked into vertex color for the water-only diffuse foam response. This is an authored bank approximation; no fluid simulation, foam particles, wave breaking, ocean bathymetry solver, or automatic riverbed terrain carving is implied. Water remains a height field at one still-water level, so waterfalls and sloping river surfaces need a different realization.

The river mesh caps subdivisions per segment (512 longitudinal, 64 across), total vertices (65,536), and source points (32). A cached maximum triangle edge supplies conservative realized spacing after caps rather than claiming the requested resolution was achieved. `reviewRiverChannel` uses the realized miter sections to check each bilinear section’s corner Jacobians and separating-axis overlap of nonadjacent convex sections. Folded/collapsed banks and overlapping sections are reported in Studio and rejected before mesh generation. Sharp bends and shore widths that cover the whole channel are warnings. River depth affects interaction queries, not the existing screen-space optical transport's opaque-scene depth.

An optional `flow.weatherResponse` coordinates authored wave amplitude and roughness with horizontal wind. Baselines are explicit (`referenceWindSpeed`), gains are bounded, and source documents are never mutated. The realization preserves wavelength, phase, speed, water level, and bank geometry, so weather changes do not reset wave motion or rebuild the channel mesh. `evaluateEnvironmentState` samples weather without atmosphere-table work. `evaluateWaterEnvironment` is shared by rendering and the runtime water resolver used for buoyancy. Vertical water velocity remains the instantaneous carrier derivative; the slow weather-amplitude envelope derivative is not included in buoyancy drag.

## Cloud realization

### Current semantic forms (September 23, 2026)

`cloudscape.formations` optionally contains up to four `tower`, `bank`, or `wisp` envelopes per authored weather key. Coordinates are atmosphere-local metres and are advected with the weather: `center` is X/Z, `base` is altitude, and `size` is horizontal half width / total height / horizontal half depth. Support stays between 850 and 6500 m. `yaw`, `density`, `erosion`, and integer `seed` control orientation, opacity, boundary detail, and variation. Stable IDs match forms across keys; up to eight runtime envelopes support entering/leaving forms. Seed edits take effect at a key boundary.

`background` controls the procedural weather coverage independently; omission preserves full background weather. `highCloudCover` and optional `highCloudYaw` control the separate thin upper layer. The same envelope upload drives view clouds, reflected clouds, cloud-light integration, and atmospheric/ground shadows. Studio exposes formation add/remove and numeric controls in both the base environment and weather keys.

See the [implementation and measured acceptance](../research/sky-implementation-2026-09-23.md) for current budgets, curved-shell distance, layered air transport, twilight changes, and limitations. The notes below record earlier stages of the renderer and their evidence.

Cloud cover supplies a three-dimensional density layer from 1.1 to 3.3 km. A maximum of 24 view samples and one forward solar-density probe per occupied sample integrate opacity and shaded interiors into a bounded 512×256 sky lookup texture. Direct surface shadowing uses one representative density sample. Broad density masses, fine shape variation and a height profile replace the original sharp, repeated white sheet pattern. The sky product feeds reflections and diffuse irradiance, and its cache includes cloud cover, wind and time. Sky/irradiance and aerial transport have separate dependency keys: camera rotation/FOV updates only the frustum volume; cloud drift updates only sky/irradiance. Periodic azimuth filtering removes the sky seam, while aerial coordinates explicitly clamp to texel centers. Cloud coordinates and altitude are anchored to the planet-relative frame and survive render-origin rebases. Cloud illumination consumes the same colored solar transmission and planet shadow as the atmosphere; it has no fabricated below-horizon sunlight floor. Water reflections use an angular footprint based on roughness instead of sampling cloud edges as perfectly sharp mirrors. No fragment performs the cloud view raymarch.

The 14 km path cap and horizon fade bound work. The extra lookup resolution is an explicit cloud-detail cost; the exact cache avoids paying it again for camera rotation alone. This is approximate single-scattering cloud lighting with a one-probe solar shadow, not full volumetric multiple scattering or precipitation simulation. Cloud positions are evaluated from the render camera for the shared sky product, an acceptable approximation at kilometre altitudes within one render region; they are not a local volumetric fog replacement.

## Editing and verification

Studio exposes sequence creation, insertion/removal and edits of every state channel, looping/interpolation, lighting zone creation/removal and transforms, exposure/tint, water current, channel points, width/depth, shore width and bank foam, plus stage-distance review. Edits use Studio's existing validated transactions, undo/redo and persistence. Mounted Studio checks cover sequence creation, duration edit, undo/redo and save/reprepare.

`environment-authoring.test.ts`, `water-authoring.test.ts`, and `atmosphere-authoring.test.ts` cover time wrapping and seeking, azimuth continuity, overlap precedence, smooth boundaries, validation, current/phase/derivative agreement, wet/dry channel limits, joined mesh queries and face winding, atmosphere bound extrema, reusable density bodies, and isolated header storage. `tools/environment-authoring-check.ts` exercises authored documents through the scene host and real WebGPU renderer, captures clear/storm river frames, rejects renderer/console errors and incomplete content, and checks that environment controls change actual rendered pixels. Visual captures establish working controls and shader validity, not AAA artistic acceptance.

## Alpine look development

`createEnvironmentLookdev()` supplies editable lighting, sky and creek documents for the shared alpine grove/ruin scene. The current source uses neutral warm side light, cool sky illumination, ambient 2.8, direct intensity 2.7 and +0.7 exposure stops. The creek follows the authored channel at a -0.2 m still-water level, with 2.2 cm / 0.9 cm waves, 0.22 roughness, 0.7 m/s current, 0.24 m shore width and 0.14 foam. Wind changes wave energy and roughness around the calm-state baseline. Review at 0 s (clear), 32 s (clouded light), and 64 s (wet clearing).

`bun tools/environment-lookdev.ts` captures a complete hardware-rendered 1024×768 review set through the shipped scene host and renderer: clear/clouded/clearing landscapes, shore detail, sky, low sun, twilight and zenith. Use `--frame=environment-shore` (or another exact frame id) to isolate a view. Authored project, camera/time, completeness, performance and diagnostic metadata accompany the captures. This artistic review is deliberately separate from the 480×320 smoke fixture.

The baseline shared-scene hardware capture (`output/lookdev-snapshots/1790110218529-16321/source/output/browser-1790110218656-16329/landscape.png`) failed the intended visual bar: dark water, a continuous white foam outline and stamped white cloud strips were evident. The revision narrows and lowers bank foam, removes its always-on shader floor, raises creek scattering tint, and replaces the binary cloud sheet with 3D density, bounded optical depth and shaded interiors. The first revision still showed flat cloud strips and aliased reflection contours in `output/lookdev-snapshots/1790110716877-17452/source/output/browser-1790110716990-17455/`; that evidence triggered the 3D density/filtered-reflection revision. Subsequent hardware captures determine the quality improvement; passing source tests alone is not AAA acceptance. The shared terrain, vegetation and composition remain part of that judgment.

The implementation follows the existing Hillaire-style LUT architecture. The targeted source review and primary references are recorded in `docs/research/sky-lighting-research-2026-09-22.md`. No improvement over Hillaire’s research is claimed: ozone absorption remains absent, cloud solar visibility uses one density probe, and the diffuse cloud contribution retains an art-directed approximation. These are documented technical limitations rather than hidden fidelity claims.

### Final review and bounded density correction

All eight 512×256 sky-product frames in `output/lookdev-snapshots/1790112811691-22548/source/output/browser-1790112811795-22566/` were reviewed. The water reflection contours and continuous foam stripe were substantially improved; clouds still failed the visual bar. Clear and low-sun clouds were smeared, and the clouded/sky/zenith views exposed large featureless masses. Low-sun lighting was muddy and twilight was very dark. The higher lookup resolution did not solve the density model’s lack of structure. Recorded individual frame GPU times were 3.01–11.14 ms on Apple Metal at 1024×768; these isolated timestamps are not a sustained-performance claim. The separate render-origin equivalence check passed.

One bounded art correction keeps the same three noise evaluations and 24 integration steps, redistributes density weight toward existing medium/fine structure, narrows the density transition, and modestly reduces cloud mass scale. This targets the observed featureless fog-like volume without changing transport, origin handling, texture resolution or integration budgets. The next captures determine whether it is an improvement. AAA sky acceptance remains unproven.

### Final captured verdict

The final set at `output/authoring-lookdev/1790113223050-23493/source/output/browser-1790113274736-23932/` contains all eight complete hardware captures. The sky, low-sun, clouded landscape and shore frames were inspected after the density and rough-reflection changes. The smaller-scale density creates more gaps and clearer silhouette variation than the previous featureless masses. Sunlit and shaded cloud regions are distinguishable, and the clouded terrain's sharp reflected-cloud contour lines are reduced by roughness filtering. The shore keeps the improved broken foam coverage rather than the original continuous white stripe.

**Visual acceptance remains below AAA.** Cloud forms still read as soft horizontal patches, with some block-shaped transitions and insufficient billowing interior detail. The low-sun view remains muddy and its shadowed terrain is too dark for confident material judgment. Water retains stretched, oval reflection shapes; they are softer than the initial tight contour aliasing but still look stylized rather than like a convincing small creek. The clouded terrain's broad wet sheen and the straight, sheer authored river banks also weaken the composition. These are visible deficiencies, not resolved by the captures passing technical checks. No additional rendering changes were made after this final review.

Reported individual final frame GPU times were 3.08–10.29 ms on Apple Metal at 1024×768 (shore 10.29 ms, low sun 7.80 ms, clouded 7.27 ms, sky 3.08 ms). All frames reported complete content and no renderer diagnostics. Timing values are per-capture observations; the fixture does not establish sustained p95 or performance on ordinary integrated hardware. The separate GPU render-origin equivalence check passed, preserving cloud/atmosphere coordinates through rebasing.

## Day, night, and weather extension

An optional `dayCycle` now moves sun elevation and azimuth independently of the weather sequence. Its duration, starting local hour, latitude, seasonal solar tilt, and north rotation are authored values. Night progress drives a moon opposite the sun, stars rotating around the local celestial pole, nighttime ambient response, and exposure adaptation. The weather sequence still controls haze, cloud cover and shape, a moving front, wind, wetness, illumination strength, and grade. This means a game can keep a continuous day clock while a storm arrives and clears. A document without `dayCycle` retains its authored fixed sun or existing sequence behavior.

`cloudscape` adds vertical development, storm depth, high thin clouds, and an oriented cover front. The cloud renderer combines a broad regional field with the existing 3D detail field, varies top height and density profile, and rejects detail evaluation when the broad field proves that the threshold cannot be reached. This is a conservative local shader bound, not a general field compiler or a validated empty-space distance hierarchy. It does not yet guarantee a recognizable authored cloud silhouette in every camera angle.

Cloud self-shading, the ground, and water now sample camera-centered products derived from the same cloud density: a 128×128×16 directional optical-depth grid and a 256×256 surface shadow field. The grid and surface product have separate dependency keys and are reused between subpixel weather and sun changes. The view is resolved into a quality-dependent texture (`384×288` at 24 steps for low, `512×384` at 32 for balanced, `768×576` at 40 for high). This reduces repeated full-resolution density work but adds GPU memory and has visible low-tier softness. The front, coverage, and cloud type are semantic authoring inputs; noise compilation and shared lighting products are concrete compiler-like wins. A general cloud field IR remains a research candidate pending a visual and performance comparison against this implementation.

Studio exposes the clock and weather controls through validated document edits. When the clock is active, weather keyframes hide the overridden sun-angle controls. The standalone Player advances the same runtime clock through `BrowserSceneHost`; neither Studio nor a game uses a separate sky implementation. `createDayNightLookdev()` provides an editable review scene, and `bun tools/environment-lookdev.ts --cycle` captures dawn, noon, storm, sunset, a sun-facing golden-hour view, night, stars, and a moon view. `--motion` captures 12 adjacent samples of the running cycle; `--quality=low` and `--quality=high` select the same quality tiers available to the renderer.

The latest eight-frame 1024×768 Apple Metal review is in `output/browser-1790122455513-6533/`. All frames completed without renderer diagnostics; observed full-frame GPU times had a 6.62 ms median and 13.43 ms maximum. A 12-frame balanced motion sample reported 12.85 ms median and 15.93 ms maximum (`output/browser-1790122478919-6573/`). An earlier 12-frame low-tier motion sample reported 11.01 ms median and 15.47 ms maximum (`output/browser-1790121803249-95383/`), before the authored timing change. These are short local samples with asynchronous GPU timestamp caveats, not a sustained p95 or a lower-tier hardware claim. The matched clear-scene capture after replacing per-ground-pixel cloud marching measured 5.96 ms on the same Apple GPU, versus about 14 ms before the shared shadow product; scene state and timing method must be matched before generalizing that gain.

The result is playable and more coherent across day, weather, and night, but it has **not passed a world-class visual bar**. The clouds still lack deliberate hero silhouettes and rich fine billows, especially in the overcast and zenith views. Sunset foregrounds remain heavy, and water/terrain lookdev limits the whole shot. Before a quality claim, review moving footage for cloud popping and sampling variance, compare fixed-exposure twilight against reference imagery, test a lower-tier GPU, and build a deliberately composed game vista whose materials and weather support the sky.

A cheap jittered cell envelope was tested for cumulus grouping (`output/browser-1790122010582-5989/cycle-noon.png`) and reverted: the cloud masses became visibly rectangular and repetitive. This is evidence that a cell hash alone is not a useful substitute for authored silhouette and seamless composition.
